## 5. 重新開始的步驟

1. **確認現場乾淨**：沒有 omobab、moba-headless、client runtime、UnrealEditor、cargo、lua 在跑，`target/locks/` 也沒有鎖。要結束程序時，先看清楚是誰啟動的，再照 PID 結束；不要依名稱全部結束。
2. **確認 live 能編譯**：

   ```bat
   tools\lua\lua.exe scripts\check_live_consistent.lua --ubt
   ```

3. **確認 commit 已完成**（第 2 節）：submodule 先 commit 並 push，主 repo 再 bump gitlink。
4. **先啟動 M3' ①**（第 6 節）。它決定之後所有英雄的做法，所以要先做。這段期間，C、遊戲模式、conformance 可以照第 4 節平行繼續。
5. 每條工作線都照原本的規則：在影子裡改，用 land_to_live 放回；實機局要排隊等實機局鎖，而且 10 分鐘內結束。

## 8. 規則與常見陷阱

- **live 輸入**（`scripts/lua_data`、`omfue` 的原始碼、Rust crate）一律在影子或副本改，再用 `land_to_live` 放回。它是全有或全無：失敗時不會寫入任何檔案。
- **同一時間只跑一組實機局**（E197），而且要在 10 分鐘內結束。headless 不受限制。不要手動刪鎖。
- **`stage_ue_shadow --sync` 會蓋掉影子裡還沒放回的修改**（E210）。sync 之前要先放回，或先備份。
- **CRLF 檔**：不要用 `sed -i`，它會把 CRLF 改成 LF（E188、E211）。
- **errors.md 的編號常撞號**：寫入之前先看目前最大的號碼，撞號時後寫的人改用最大號 +1。
- **數值只寫在 v3 `values`**：說明文字、產生的 Rust、手寫 hook 與註解裡都不能寫數字；hook 只能引用產生的常數。
- **DLL 不保存狀態**：技能狀態都放在 host，產生的程式碼裡不能有 `static mut` 或 thread local，不然熱加載會遺失狀態。
- **照原作**：不能為了讓重播一樣而改資料。差異來自 handler 的 bug 時，要改 handler。
- **用子 agent 時**，每個 agent 要用自己的暫存目錄，不能共用（E215）。

## 9. 名詞

### IR（已停用）

IR（intermediate representation，中間表示）是先前 M3 採用的做法：

```text
v3 文件 → 建置期編成 IR（JSON 指令陣列）→ 遊戲執行時由 ir.rs 直譯
```

它的好處是改技能不用編譯；缺點是每個指令都要經過直譯迴圈，而且寫錯要到載入時才會發現。使用者決定不用（D15）。Lua 端整理好的 IR 樹還可以當成產生器的內部表示，不會出貨。

### 產生 Rust（新的做法）

```text
v3 文件（唯一的作者資料）
  → 建置期 Lua 產生器 v3_rust.lua
  → 每位英雄一個 Rust crate（數值、狀態、屬性都是具型別的常數）
  → rustc 編譯成 hero_<id>.dll
  → host 依 manifest 載入；開發時熱加載
```

- 原生程式碼，沒有直譯成本。
- 引用錯數值、狀態、屬性時 rustc 就編不過。
- 改一位英雄只重編一個 DLL。
- 說明、網站、TooltipRenderer 仍然讀同一份 values，數值單一來源不變。

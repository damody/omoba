## ADDED Requirements

### Requirement: Generated C ABI header from Rust bridge
`om-bridge` SHALL expose a public C ABI generated by `cbindgen`. Exported functions SHALL use `extern "C"` and stable symbol names. Exported data structs SHALL be `#[repr(C)]` and use fixed-width scalar fields, opaque handles, pointers, lengths, offsets, and explicit version/size fields. The generated header SHALL NOT expose Rust-only ownership or layout types such as `Vec`, `String`, `Arc`, `Box`, references, trait objects, generic types, or Rust enum payload layout.

#### Scenario: cbindgen generates om_bridge.h
- **WHEN** 開發者執行 documented cbindgen command for `om-bridge`
- **THEN** system MUST generate `om_bridge.h`
- **AND** header MUST include bridge ABI version constants and public C declarations

#### Scenario: Header has no Rust-owned container types
- **WHEN** 檢查 generated `om_bridge.h`
- **THEN** header MUST NOT contain `Vec`、`String`、`Arc`、`Box`、Rust references、Rust lifetime syntax 或 generic Rust type names
- **AND** variable-size arrays MUST be represented as pointer + count or offset + length

#### Scenario: C or C++ compile smoke includes header
- **WHEN** a minimal C/C++ smoke source includes `om_bridge.h`
- **THEN** it MUST compile without requiring Rust headers or Unreal headers
- **AND** it MUST be able to type-check calls to version, create/destroy, acquire/release frame, diagnostics, and input APIs

### Requirement: Opaque runtime lifecycle API
The bridge SHALL expose opaque runtime handles and explicit lifecycle functions for create, start, stop, destroy, status, last error, and diagnostics. All fallible calls SHALL return a status code or boolean result; Rust panics SHALL NOT unwind across the C ABI boundary.

#### Scenario: Runtime handle lifecycle succeeds
- **WHEN** caller provides a valid `RuntimeConfig`
- **THEN** `om_runtime_create` MUST return a non-null opaque handle or a clear error status
- **AND** `om_runtime_start` MUST start bridge worker threads
- **AND** `om_runtime_stop` and `om_runtime_destroy` MUST release resources without leaking worker threads

#### Scenario: Invalid config is rejected
- **WHEN** caller provides null required pointers, invalid struct size, unsupported ABI version, or invalid paths
- **THEN** create/start MUST fail with a non-success status
- **AND** last error API MUST return a diagnostic string valid until the next mutating bridge call on that runtime or thread-local error slot

#### Scenario: Panic does not cross FFI
- **WHEN** internal Rust code panics during an exported function
- **THEN** bridge MUST catch the panic at the FFI boundary when practical
- **AND** exported function MUST return an error status instead of unwinding into UE C++

### Requirement: Atomic frame publication with pointer leases
The bridge SHALL publish dynamic render frames through Rust-owned immutable buffers. A consumer SHALL acquire the latest frame through a C ABI function that performs acquire memory ordering, returns a pointer plus lease token, and SHALL release that lease after reading. Producer publication SHALL use release ordering after all frame writes complete. Frame sequence numbers SHALL be monotonic for each runtime.

#### Scenario: Consumer observes complete frame after acquire
- **WHEN** producer publishes frame sequence N
- **THEN** `om_acquire_latest_frame` MUST return either no frame or a pointer to a complete immutable frame with sequence N or newer
- **AND** all fields reachable from the returned frame pointer MUST be visible consistently for that lease

#### Scenario: Release makes slot reusable
- **WHEN** UE releases a previously acquired frame lease
- **THEN** bridge MUST decrement that slot's reader count or equivalent lifetime guard
- **AND** producer MAY reuse the slot only after no active leases reference it

#### Scenario: Producer does not block simulation when UE is slow
- **WHEN** all frame slots are temporarily held by consumers
- **THEN** bridge MUST NOT block the simulation tick loop indefinitely
- **AND** bridge MUST skip or drop publication with diagnostics rather than corrupting a leased frame

#### Scenario: Raw Rust atomic layout is not part of the ABI
- **WHEN** UE code synchronizes with bridge frame publication
- **THEN** UE MUST use exported acquire/release functions or an explicitly specified C-compatible control block
- **AND** generated C ABI MUST NOT require UE to dereference Rust `AtomicU64` or Rust atomic struct fields directly

### Requirement: FFI frame and catalog data model
The bridge SHALL separate hot dynamic frame data from cold catalog metadata. Dynamic frames SHALL contain tick, sequence, entity scalar arrays, removed ids, per-entity animation state arrays, ability event/cue arrays, active buff snapshots, buff lifecycle event arrays, UnitScript event cue arrays, round/lives state, render FX cues, applied input metadata, map route point arrays, and references to catalog ids. Catalog data SHALL contain unit, ability, tower, buff, upgrade, hero render, animation metadata, UnitScript event metadata, and asset metadata with a generation/hash. All strings exposed through frame or catalog pointers SHALL live inside Rust-owned frame/catalog storage for the duration of the lease.

#### Scenario: Dynamic frame exposes hot entity data
- **WHEN** local replica publishes a frame after tick N
- **THEN** frame MUST include tick N, sequence, entity count, entity pointer, removed id count/pointer, and round/lives state
- **AND** each entity entry MUST include entity id/gen, kind, position, facing, HP/max HP, owner, attack range, and stable unit/catalog id where applicable

#### Scenario: Dynamic frame exposes animation states
- **WHEN** local replica publishes animation intent for visible entities
- **THEN** frame MUST include animation state count/pointer
- **AND** each animation state MUST include entity id/gen, locomotion state, locomotion variant, animation overlay/stance, action state, attack phase, action instance id, phase timing/progress, animation tag/catalog id, flags, and play rate
- **AND** UE MUST be able to consume the record without reading Rust gameplay components or Rust enum payload layout

#### Scenario: Dynamic frame exposes ability events
- **WHEN** local replica accepts, toggles, resolves, or visually procs an ability before frame publication
- **THEN** frame MUST include ability event count/pointer
- **AND** each ability event MUST include event kind, tick, sequence, caster entity id/gen, ability catalog id, level, action/cue instance id, target entity/point when applicable, and FFI-safe payload references
- **AND** SaikaMagoichi ability events MUST be projectable to typed C++ payloads for `sniper_mode`, `saika_reinforcements`, `rain_iron_cannon`, and `three_stage_technique`

#### Scenario: Dynamic frame exposes buff lifecycle data
- **WHEN** local replica buff state changes between two published frames
- **THEN** frame MUST include active buff snapshot count/pointer and buff event count/pointer
- **AND** each buff event MUST be usable without reading Rust `BuffStore` internals

#### Scenario: Dynamic frame exposes UnitScript event cues
- **WHEN** local replica captures one or more `UnitScript` hook invocations before frame publication
- **THEN** frame MUST include UnitScript event count/pointer
- **AND** each UnitScript event MUST be usable without reading `GameWorldDyn`, script trait objects, or Rust ABI internals

#### Scenario: Dynamic frame exposes map route geometry
- **WHEN** local replica initializes or extracts a render frame for a map with one or more Lua/world paths
- **THEN** frame MUST include map route count/pointer and route point count/pointer
- **AND** each route MUST reference a contiguous point range by start index and count
- **AND** each point MUST use the same backend 2D world coordinate system as entity positions
- **AND** UE MUST be able to build route visuals without reading Lua files or Rust map resources directly

#### Scenario: Catalog exposes metadata once per generation
- **WHEN** runtime initializes or Lua content generation/hash changes
- **THEN** bridge MUST publish or expose a catalog with matching generation/hash
- **AND** repeated dynamic frames with the same generation MUST reference catalog ids instead of duplicating all metadata strings every frame
- **AND** animation states MUST reference animation catalog ids or frame string-table references rather than duplicating long state/montage names every frame
- **AND** ability events MUST reference ability catalog ids and generated payload schemas rather than requiring UE to parse ad hoc log text
- **AND** buff events MUST reference buff catalog ids when the buff id is known to the generated catalog
- **AND** UnitScript event payloads MUST reference unit/ability/buff/order/state strings through catalog ids or frame string-table references

#### Scenario: Empty arrays are represented safely
- **WHEN** a frame or catalog section has zero items
- **THEN** its count MUST be zero
- **AND** pointer MAY be null
- **AND** UE consumer MUST be able to distinguish empty data from malformed non-zero count with null pointer

#### Scenario: String pointers remain lease-scoped
- **WHEN** UE reads a UTF-8 string slice from a frame or catalog
- **THEN** pointer and length MUST remain valid until the corresponding frame/catalog lease is released
- **AND** UE MUST NOT free or retain the raw pointer after release

### Requirement: Memory ownership and unload safety
All memory reachable through frame, catalog, diagnostics, and error pointers SHALL be owned by the bridge unless an API explicitly documents caller-owned buffers. UE SHALL NOT free bridge-owned pointers. Runtime destroy SHALL either wait for outstanding leases to release or fail/return busy according to the documented API; it SHALL NOT unload while UE can still read bridge memory.

#### Scenario: Caller does not free frame memory
- **WHEN** UE receives a frame pointer from bridge
- **THEN** UE MUST read it as borrowed memory
- **AND** UE MUST release it with bridge release API
- **AND** UE MUST NOT call `free`, `delete`, or Unreal allocator functions on any bridge-owned pointer

#### Scenario: Destroy handles outstanding leases
- **WHEN** caller requests runtime destroy while a frame lease is still active
- **THEN** bridge MUST either block until leases are released or return a documented busy/error status
- **AND** bridge MUST NOT deallocate the leased frame while it is still readable by UE

#### Scenario: Stop prevents new publication
- **WHEN** caller stops the runtime
- **THEN** bridge MUST stop accepting new worker publication
- **AND** existing acquired leases MUST remain valid until release

### Requirement: C ABI input submission
The bridge SHALL expose C ABI functions or structs for gameplay input submission without requiring UE to serialize protobuf. Input APIs SHALL accept backend world units, stable ids, command flags, and typed target payloads; convert them into shared `PlayerInput`; assign/report input ids; and submit through the lockstep client using the configured low-latency target tick policy.

#### Scenario: Input command converts to PlayerInput
- **WHEN** caller submits a move, attack move, attack target, tower, tower target priority, item, start-round, cast ability, or upgrade ability command through C ABI
- **THEN** bridge MUST validate arguments
- **AND** bridge MUST convert the command to shared `PlayerInput`
- **AND** bridge MUST enqueue it for lockstep submission

#### Scenario: Input receiver preserves queued command flags
- **WHEN** caller submits a move, attack move, or attack target command with queued/Shift append flag
- **THEN** bridge MUST preserve that flag in the shared `PlayerInput`
- **AND** queued command order MUST be observable by the local replica/backend as an append operation, not a replacement operation

#### Scenario: Ability input supports point, entity, and no-target casts
- **WHEN** caller submits a cast ability input
- **THEN** bridge MUST accept ability catalog id or slot plus target kind
- **AND** target kind MUST support no-target/self, point, and entity forms
- **AND** invalid target kind/payload combinations MUST be rejected before enqueue

#### Scenario: Tower placement input carries placement point and tower id
- **WHEN** caller submits a place tower input
- **THEN** bridge MUST accept tower catalog id, player id, backend-world placement point, and optional path/slot metadata
- **AND** bridge MUST leave placement legality to the Rust/local replica validation path

#### Scenario: Tower management inputs carry typed fields
- **WHEN** caller submits tower upgrade, tower sell, or tower target priority input
- **THEN** bridge MUST accept tower entity id/gen, player id, upgrade path/level or target priority enum as applicable
- **AND** bridge MUST validate slot/path/priority ranges before enqueue
- **AND** bridge MUST leave ownership and final application to the Rust/local replica validation path

#### Scenario: Item and ability-upgrade inputs are distinct actions
- **WHEN** caller submits item use or ability upgrade input
- **THEN** bridge MUST preserve item slot or ability slot/index and optional item target payload
- **AND** bridge MUST convert item use to `PlayerInput::ItemUse` and ability upgrade to `PlayerInput::UpgradeAbility`
- **AND** bridge MUST NOT convert either action into `CastAbility`

#### Scenario: Input id is observable
- **WHEN** bridge accepts an input command
- **THEN** API MUST return or later expose an input id
- **AND** corresponding applied input metadata MUST appear in diagnostics or future frames when local replica observes the input

#### Scenario: Invalid input is rejected without state mutation
- **WHEN** caller submits an unsupported command kind, invalid slot/path index, null pointer, or non-finite coordinate
- **THEN** bridge MUST return an error status
- **AND** bridge MUST NOT enqueue a malformed `PlayerInput`

### Requirement: Diagnostics and performance counters
The bridge SHALL expose diagnostics suitable for UE HUD/logging and stress validation, including connection state, latest tick, latest sequence, sim TPS, frame publish count, dropped/skip publish count, active lease count, input queue length, network byte counters, RTT, last error, and Lua content generation/hash.

#### Scenario: Diagnostics are pollable without frame lease
- **WHEN** UE calls diagnostics API without acquiring a frame
- **THEN** bridge MUST return a consistent diagnostics snapshot
- **AND** call MUST NOT require locking the frame buffer for a long duration

#### Scenario: Dropped publication is visible
- **WHEN** producer skips frame publication because no slot is available or because runtime is stopping
- **THEN** diagnostics MUST increment a dropped/skipped publication counter
- **AND** UE log/HUD can surface the issue during stress testing

#### Scenario: Connection state is visible
- **WHEN** backend connection is disconnected, joining, connected, or errored
- **THEN** diagnostics MUST expose that state through a stable enum or status code
- **AND** UE runtime subsystem can show it without parsing free-form log text

### Requirement: ABI verification tests
The bridge SHALL include verification for Rust ABI layout, generated header freshness, C/C++ include/link smoke, frame lease safety, input validation, and runtime lifecycle. These tests SHALL be runnable without UE Editor where possible, with UE build verification using `D:\UE5.7` by default and gated by the resolved UE 5.7 path.

#### Scenario: Rust FFI tests pass
- **WHEN** 開發者執行 `cargo test --manifest-path <UE_PROJECT_ROOT>/bridge/Cargo.toml`
- **THEN** tests MUST validate ABI version, struct sizes, null/invalid argument handling, frame acquire/release, and lifecycle cleanup

#### Scenario: Header freshness check catches drift
- **WHEN** Rust exported ABI changes without regenerating `om_bridge.h`
- **THEN** verification MUST fail or report that generated header is stale

#### Scenario: UE build verification is optional but explicit
- **WHEN** UE 5.7 build path resolves to `D:\UE5.7` or a configured override
- **THEN** verification MUST attempt to compile the `Om UE frontend` UE module against staged header/library
- **AND** when UE path is not configured, verification MUST report the UE build step as skipped rather than passed

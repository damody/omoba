## Context

`scripts/lua_data/templates.json` is currently the source of truth for tower, hero, summon, ability, projectile, and creep stats generated by `omoba-template-ids`. Per-story files such as `entity.json`, `ability.json`, `mission.json`, and `map.json` are still loaded by `omb` at runtime.

TD and MOBA `map.json` files still define `Creep` entries with duplicated unit data such as `Label`, `HP`, `DefendPhysic`, `DefendMagic`, and `MoveSpeed`. `TD_STRESS` demonstrates the failure mode: the template catalog defines `td_stress.hp = 10000.0`, while `TD_STRESS/map.json` overrides the same unit to `HP = 10000000.0`.

The new boundary is intentionally narrow: only `omoba-template-ids` may load Lua, and only at build time. Every other crate consumes generated Rust data and remains pure Rust at runtime.

## Goals / Non-Goals

**Goals:**

- Replace all shipped JSON content under `scripts/lua_data` with Lua builder files that return Lua tables.
- Use `mlua` only in `omoba-template-ids` build-time codegen.
- Generate Rust data/API for both template data and shipped story data.
- Keep the existing `omoba-template-ids` template lookup API stable while adding generated story accessors.
- Allow Lua builders to call approved context helpers such as `ctx.include`, `ctx.read_text`, and `ctx.read_toml`.
- Make each map `Creep` declaration a template reference instead of a duplicated unit definition.
- Fail fast when a map references a creep id that is missing from generated template data.

**Non-Goals:**

- Add runtime Lua loading to `omb`, `omfx`, map editor, scripts, or any crate other than `omoba-template-ids` build-time codegen.
- Keep JSON content files as runtime inputs.
- Add JSON/Lua dual-loading compatibility after migration.
- Add per-map stat overrides for creeps.
- Change lockstep transport, snapshot extraction, or rendering contracts except where labels/stats naturally come from generated template values.

## Decisions

### Use `scripts/lua_data` as the Content Source Root

The content source root is `scripts/lua_data`. It contains build-time Lua sources for templates and shipped stories. The folder name is intentional: content is authored as Lua table builders, but runtime crates do not load Lua.

All source content files under this root should be Lua after migration. `scripts/lua_data/**/*.json` should be removed or kept only as non-canonical migration artifacts outside runtime/build inputs.

Alternative considered: keep story JSON files and only convert templates. That preserves two source formats and leaves runtime story loading dependent on JSON files, so it is rejected.

### Keep Lua Build-Time Only

`omoba-template-ids/build.rs` will be the only production code path that loads Lua files. It may depend on `mlua` with a vendored Lua runtime so Windows builds do not require a system Lua installation.

All other crates will use generated Rust APIs from `omoba-template-ids`. `omb` runtime story initialization will request generated story data by story id and will not read `.json` or `.lua` content source files.

Alternative considered: let `omb` runtime read Lua story files too. That increases runtime dependencies, broadens the execution surface, and is unnecessary because shipped content can be compiled into Rust data.

### Use Lua Builder Functions for All Content Codegen

`scripts/lua_data/templates.lua` and each per-story content file will return builder functions. `build.rs` loads each Lua file with `mlua`, calls the builder with a context table, and reads the returned Lua table into Rust codegen structs.

Array-like data must be encoded as ordered Lua sequences so generated ids and story lists remain deterministic.

Example creep template module:

```lua
return function(ctx)
  local extra = ctx.read_toml("templates/creeps_extra.toml") or {}
  return {
    {
      id = "td_stress",
      display_name = "壓測怪",
      hp = 10000.0,
      armor = 0.0,
      magic_resistance = 0.0,
      damage = extra.td_stress_damage or 0.0,
      attack_range = 0.0,
      move_speed = 100.0,
      enemy_type = "melee",
      ai_type = "passive",
      exp_reward = 0,
      gold_reward = 0,
    },
  }
end
```

Alternative considered: parse Lua table syntax with a custom parser. That avoids executing Lua but gives up computed data, supplemental config reads, and composition, so an `mlua` builder invocation is preferred.

### Provide Narrow Codegen Context Helpers

The builder context will expose approved helpers:

- `ctx.include(path)`: load another Lua builder file, call it with the same context, and return its table.
- `ctx.read_text(path)`: read a text file relative to the content root.
- `ctx.read_toml(path)`: read a TOML file relative to the content root and convert it into Lua values.

All path helpers will resolve paths relative to `scripts/lua_data/`, reject absolute paths and parent-directory escapes, detect include cycles for `ctx.include`, and record every file read so `build.rs` can emit `cargo:rerun-if-changed`.

Alternative considered: expose normal Lua `require` and filesystem APIs. That depends on Lua package search paths and weakens content-root validation, so narrow context helpers are preferred.

### Generate Story Data Without Depending on `omb`

`omoba-template-ids` cannot depend on `omb` types without creating a dependency cycle. Generated story data should therefore use dependency-light structs defined in `omoba-template-ids` or a small generated-data module. `omb` can adapt these generated structs into existing runtime structures such as `CampaignData` and `CreepWaveData`, or runtime initialization can be refactored to consume the generated structs directly.

This preserves the pure-Rust runtime boundary while avoiding JSON parsing at runtime.

Alternative considered: generate Rust code that directly constructs `omb::ue4` structs. That would couple `omoba-template-ids` to `omb` and break crate layering, so a neutral generated data model is preferred.

### Preserve Existing Template API

`omoba-template-ids/build.rs` will replace `serde_json` parsing with `mlua` builder execution. It will still emit the same generated ids, constants, `*_by_name`, `*_display`, `tower_stats`, `hero_stats`, `creep_stats`, `summon_stats`, ability lookup API, and projectile kind lookup API into `template_ids_gen.rs` or an equivalent included generated module.

No checked-in or generated JSON intermediary should be required for codegen.

### Slim Map Creep Definitions

Map `Creep` entries will keep the existing `Name` field, but it will be interpreted as the generated template creep id. This avoids changing `CreepWave[].Detail[].Creeps[].Creep`, which already references the same name string.

The map data model should reject stat/display fields such as `Label`, `HP`, `DefendPhysic`, `DefendMagic`, `MoveSpeed`, `damage`, `attack_range`, `enemy_type`, `ai_type`, `exp_reward`, and `gold_reward`.

Alternative considered: ignore old fields silently. That would let stale values remain in source content and recreate the ambiguity this change is meant to remove.

### Resolve Runtime Emitters from Generated Data

`StateInitializer::setup_creep_emiters` will resolve each map creep reference with `omoba_template_ids::creep_by_name`, `creep_stats`, and `creep_display`. The emitter's `CProperty` will be built from `CreepStats.hp`, `move_speed`, `armor`, and `magic_resistance`; labels will use `creep_display`; combat metadata remains available from generated stats for ECS unit construction.

`omb` runtime must not evaluate Lua or parse JSON source files to resolve these stats.

## Risks / Trade-offs

- [Risk] Generating full story data broadens `omoba-template-ids` beyond ids/templates. -> Mitigation: keep generated story structs dependency-light and preserve existing public APIs.
- [Risk] Generated id or story order can shift if Lua tables are written as key maps instead of ordered sequences. -> Mitigation: require array-like sequences for ordered categories/lists and add tests for important ids such as `td_stress`.
- [Risk] Lua codegen can become hard to reproduce if it reads arbitrary files. -> Mitigation: expose only path-validated context helpers, reject unsafe paths, and emit `cargo:rerun-if-changed` for every included/read file.
- [Risk] Existing maps may rely on values that only exist in map JSON. -> Mitigation: audit all current story maps, add missing creep ids to Lua templates, and resolve conflicts explicitly before deleting duplicated fields.
- [Risk] Removing map-local `Label` values changes UI labels when a map intentionally used a context-specific name. -> Mitigation: either add a dedicated template id for that contextual unit or update the canonical `display_name` in the Lua template catalog.
- [Risk] The `scripts/lua_data` name can imply runtime Lua loading. -> Mitigation: document the boundary and add a guard that only `omoba-template-ids` may depend on `mlua` or load Lua.

## Migration Plan

1. Inventory all shipped `scripts/lua_data/**/*.json` files and every `Creep[].Name` in shipped maps.
2. Define the Lua source layout: `scripts/lua_data/templates.lua`, template modules, and per-story `entity.lua`, `ability.lua`, `mission.lua`, and `map.lua` builders.
3. Convert `templates.json` to Lua builder modules without changing declaration order; keep `td_stress.hp = 10000.0` authoritative.
4. Convert each shipped story JSON file to an equivalent Lua builder table.
5. Update `omoba-template-ids/build.rs` to load Lua with `mlua`, call builder functions, expand includes, track read config files, and emit template plus story generated Rust data.
6. Update runtime initialization to consume generated story data and generated template lookups; remove runtime dependency on content JSON files.
7. Convert map creep definitions to template references and reject duplicated unit fields.
8. Update tooling/docs/build freshness references from JSON inputs to Lua source and included helper/config files.
9. Add tests that verify Lua codegen determinism, generated story loading, map creep references, forbidden map-local creep fields, old JSON path removal, and absence of runtime Lua dependency outside `omoba-template-ids`.

Rollback is straightforward before data migration is shipped: restore JSON content files, the old `omoba-template-ids/build.rs` JSON parser, and old runtime story loading from version control. After migration, rollback would require reintroducing JSON story sources, so the strict-loader step should land only with the migrated Lua files and tests.

## Open Questions

- Whether generated story data should live in the existing generated file or a companion generated module. Either is acceptable if the existing template lookup API remains stable.
